## КОНТЕКСТ ПРОЕКТА

### Суть проекта
Система реализует **межбиржевой спотово-фьючерсный арбитраж** (или фьючерс-фьючерс арбитраж): одновременно открывает SHORT на одной бирже и LONG на другой, когда разница цен (спред) превышает заданный порог. Прибыль фиксируется при схлопывании спреда или при превышении накопленного PnL порога прибыли.

### Список бирж
Система работает со следующими биржами:
- **Bitget**
- **Bybit**
- **Gate**
- **MEXC**
- **Binx**
- **AsterDEX**
- **Ourbit**

Критерии выбора бирж: высокая ликвидность, наличие REST и WebSocket API, большое количество торговых пар, стабильная работа интерфейсов.

### Технологический стек
- **WebSocket Market Streams** — получение данных в реальном времени (orderbook, цены, funding rate)
- **REST API** — исполнение ордеров, управление позициями, получение баланса
- **Multi-threaded architecture** — параллельная обработка потоков данных по каждой бирже
- **Real-time spread analysis** — вычисление арбитражного спреда с учётом funding rate
- **Automated trading execution** — автоматическое открытие и закрытие позиций

## АЛГОРИТМ СИСТЕМЫ

### 1. Формирование торгового пула

**Шаг 1.** Через API каждой биржи получить список доступных торговых инструментов (фьючерсных пар).

**Шаг 2.** Найти пересечение — монеты, которые одновременно торгуются на нескольких биржах.

**Шаг 3.** Отфильтровать монеты по ликвидности и активности торгов. Результат — финальный пул торговых пар.

### 2. Формирование пар бирж

Из пула бирж система формирует все возможные комбинации пар (например, Bitget–Bybit, Bitget–Gate, Bybit–Gate и т.д.). Для каждой пары бирж система проходит по списку монет, присутствующих на обеих площадках.

### 3. Расчёт арбитражного спреда

Для каждой пары бирж (A, B) и каждой монеты система получает:
- `Bid_A` — лучшая цена продажи на бирже A
- `Ask_A` — лучшая цена покупки на бирже A
- `Bid_B` — лучшая цена продажи на бирже B
- `Ask_B` — лучшая цена покупки на бирже B
- `FR_A` — текущий funding rate на бирже A
- `FR_B` — текущий funding rate на бирже B

**Учёт funding rate:**

```
Сценарий A→B (SHORT на A, LONG на B):
  Funding_diff_AB = FR_B − FR_A

Сценарий B→A (SHORT на B, LONG на A):
  Funding_diff_BA = FR_A − FR_B
```

**Эффективный спред:**

```
EffectiveSpread_AB = (Bid_A − Ask_B) − Funding_diff_AB
EffectiveSpread_BA = (Bid_B − Ask_A) − Funding_diff_BA
```

**Выбор стратегии:**

```
BestSpread = max(EffectiveSpread_AB, EffectiveSpread_BA)

Если BestSpread > OpenThreshold → открывать позицию по лучшей стратегии
```

### 4. Условия открытия арбитражной сделки

Перед открытием сделки система последовательно проверяет все условия:

**1. Спред выше порога:**
```
BestSpread > OpenThreshold
```

**2. Рыночная нейтральность (равный объём позиций):**
```
Position_A = Position_B
где Position = Price × Quantity
```
SHORT и LONG должны быть одинакового размера, иначе возникает рыночный риск.

**3. Достаточность баланса с учётом плеча:**
```
Position_size ≤ Balance × Leverage_max
```

**4. Максимальный объём позиции по инструменту:**
```
Position_size ≤ Max_position_size (лимит биржи)
```

**5. Ликвидность стакана:**
```
Order_size ≤ Available_liquidity
MinLiquidity > TradeSize × 1.5
```
Если ордер больше доступной ликвидности — возникает slippage, спред может исчезнуть до исполнения.

**6. Лимит ордеров на монету:**
```
Текущие ордера по монете < Max_orders_per_coin
```
Предотвращает накопление избыточного риска и перегрузку API биржи.

**7. Синхронность открытия:**
Позиции на двух биржах должны открываться практически одновременно с использованием параллельных запросов. Если одна позиция открылась, а другая нет — немедленно закрыть открытую.

**Алгоритм проверки перед открытием (в порядке):**
```
1. Проверить spread
2. Проверить funding
3. Проверить баланс
4. Проверить leverage
5. Проверить ликвидность
6. Проверить max position
7. Проверить синхронность ордеров
```

## ТОРГОВЫЕ СТРАТЕГИИ

### Стратегия 1: Фиксация максимального спреда (через PnL)

Система не ждёт полного схлопывания спреда, а многократно фиксирует прибыль внутри одного расширенного спреда.

**Цикл стратегии:**
```
Spread > OpenThreshold
  ↓
Open LONG / SHORT
  ↓
Monitor PnL
  ↓
SpreadProfit > ProfitThreshold ?
  ↓
Close positions → Reopen positions → Repeat
```

**Расчёт SpreadProfit:**
```
SpreadProfit = PnL_A + PnL_B
```

**Расчёт ProfitThreshold:**
```
AvgSpread = (1/N) × Σ Spread_i   (по N последним тикам, например N=50–100)

ProfitThreshold = AvgSpread × k
где 0 < k < 1, обычно k = 0.7 – 0.9
```

Пример: `AvgSpread = 1.0`, `k = 0.8` → `ProfitThreshold = 0.8`

---

### Стратегия 2: Альтернативная — контроль через Delta Spread

Вместо PnL система ориентируется на изменение рыночного спреда. Это снимает зависимость от размера позиции и искажений от комиссий и funding.

**Спред открытия (для сценария SHORT_A / LONG_B):**
```
OpenSpread = Bid_A − Ask_B
```

**Текущий спред:**
```
CurrentSpread = Bid_A_current − Ask_B_current
```

**Delta Spread (основная метрика):**
```
DeltaSpread = OpenSpread − CurrentSpread
```
Если `DeltaSpread > 0` — спред сужается, позиция становится прибыльной.

**Условие закрытия:**
```
DeltaSpread ≥ CloseThreshold
или
CurrentSpread ≤ CloseSpreadTarget
```

**Пример:**
```
Открытие:    Bid_A=65080, Ask_B=65000 → OpenSpread=80
Через время: Bid_A=65040, Ask_B=65020 → CurrentSpread=20
DeltaSpread = 80 − 20 = 60
CloseThreshold = 50 → система закрывает позиции ✓
```

**Преимущества стратегии 2:**
- Независимость от размера позиции
- Стабильная оценка арбитража
- Точный контроль момента закрытия
- Меньшее влияние комиссий и funding

## АРХИТЕКТУРА СИСТЕМЫ

### Поток данных

```
[Биржи: Bitget, Bybit, Gate, MEXC, Binx, AsterDEX, Ourbit]
           │           │           │
      WebSocket    WebSocket    WebSocket
           │           │           │
           └─────── Market Data Engine ───────┘
                          │
                   Arbitrage Engine
                          │
                   Trade Decision
                          │
                   Trading Engine
                          │
                      REST API
                          │
                   Order Execution
```

### Почему WebSocket, а не REST для получения данных

REST работает по принципу polling — система сама опрашивает биржу с интервалом. Это создаёт критические проблемы:
- **Задержка:** арбитраж существует 200–800 мс, REST может не успеть
- **Rate limits:** биржи ограничивают количество запросов (20–50 запросов/сек), а нужно отслеживать 1000+ пар на 7 биржах
- **Нагрузка:** постоянные HTTP-запросы создают лишнюю сетевую и вычислительную нагрузку

WebSocket работает по принципу push — биржа сама отправляет обновления сразу при изменении. Типы событий: `Price update`, `Orderbook update`, `Funding rate update`, `Trade update`.

REST API используется **только** для исполнения ордеров и управления позициями.

### Многопоточность

Система использует многопоточную архитектуру:
- Отдельный поток на WebSocket-подключение к каждой бирже
- Отдельные потоки для обработки данных по каждой монете/паре бирж
- Параллельное исполнение ордеров на двух биржах одновременно

## УПРАВЛЕНИЕ РИСКАМИ

### Риск проскальзывания (Slippage)
- Перед открытием проверять глубину стакана: `OrderbookDepth ≥ PositionSize`
- Если ликвидность недостаточна — не открывать позицию

### Риск несинхронного исполнения (Execution Risk)
```
Open Order A
  ↓
Open Order B
  ↓
If Order B failed → Close Order A immediately
```
Также нужен: Timeout открытия, контроль статуса ордера, Fail-safe закрытие.

### Управление объёмами
```
MaxPositionSize   — лимит на размер одной позиции
MaxLeverage       — максимальное кредитное плечо
MaxOpenPositions  — максимальное количество открытых позиций одновременно
Max_orders_per_coin — лимит ордеров по одной монете
```

### Контроль ликвидности
```
MinLiquidity > TradeSize × 1.5
```

## ТЕСТИРОВАНИЕ И МАСШТАБИРОВАНИЕ

### Backtesting
Перед запуском в продакшн система проверяется на исторических данных. Что анализируется:
- `Spread frequency` — частота появления арбитражных возможностей
- `Profitability` — реальная прибыльность с учётом комиссий
- `Strategy stability` — устойчивость стратегии к различным рыночным условиям

### Масштабирование
Система проектируется с расчётом на горизонтальное масштабирование:
- Добавление новых бирж
- Расширение списка монет
- Увеличение числа потоков
- Подключение дополнительных торговых аккаунтов

- Всегда указывай, к какому компоненту системы относится твой ответ (Market Data Engine / Arbitrage Engine / Trading Engine / Risk Management / Monitoring).
